# [Grasp: Hardening Serverless Applications through Graph Reachability Analysis of Security Policies](https://dl.acm.org/doi/abs/10.1145/3589334.3645436)
--- 
## 소개
* Serverless Application 보안 정책에 대한 추론을 위한 논리 기반 도달 가능성 그래프 모델을 정의합니다. 플랫폼에 구애받지 않는 기본 요소와 데이터 및 실행의 흐름을 파악하는 관계를 정의하고, 분석 엔진은 구성과 리소스에 대한 잠재적인 공격 경로를 식별합니다.
* 유효한 IAM 정책 731개를 포함한 총 1649개의 Serverless Application 오픈 소스를 수집했습니다.
* 권환이 과도하게 부여된 글로벌 정책의 사용과 어플리케이션 간의 높은 수준의 연결성을 발견함으로써 Serverless보안 정책에 대한 최초의 실증적 연구입니다.

## 배경 및 동기
### 전역 정책과 기능 정책 
Serverless Application 개발자들은 두 가지의 액세스 제어 정책을 사용합니다. 개별 기능 정책과, 모든 기능에 적용되는 전역 정책을 사용합니다. 전역 정책은 개별 함수가 작동하는 데 꼭 필요하지 않은 권한에 대한 액세스 권한을 부여하여 과도한 권한을 부여하기 쉽습니다. 하지만 많은 기능 정책으로 구성된 정책은 추론하기가 더 어렵습니다. 이 두 가지 정책 유형을 단일 어플리케이션에 배포할 수 있고 이 때에는 기능 수준 정책이 전역 정책보다 우선순위가 높습니다.
### 와일드카드
와일드카드는 Fun A 처럼 명시적으로 정하는 것이 아닌 Fun *, * 처럼 여러 주체와 일치하는 주제를 말합니다. 와일드카드 권환은 필요한 권한이 확실하지 않을 때, 문제를 피하기 위해서 자주 사용하는데 이때 객체에 의도하지 않은 권한을 부여할 수 있습니다.
### 관리 정책
관리 정책은 클라우드 제공업체가 유지 보수 하는 정책으로 미숙한 개발자들을 지원하기 위해 공통 권한을 그룹화 합니다. 이는 와이드카드보단 개선된 것이지만 여전히 의도치 않은 권한이 부여될 수 있습니다. 이뿐만 아니라 이 정책은 개발자가 직접 제어할 수 없기 때문에 변경했을 시 예상치 못한 결과를 초래할 수 있습니다.
### 접근 방식    
위 문제들을 해결하기위해 Grasp는 어플리케이션 간에 허용되는 상호작용을 설명하는 도달 가능성 그래프를 보여줍니다. 아래 그림을 예로 설명하겠습니다. 이 그림은 어플리케이션 매니페스트를 도달 가능성 그래프로 변환하는 하는 방법의 예를 보여줍니다. 코드에서는 모든 정책이 모든 리소스에 대해 모든 작업을 허용하지만 단순화된 예시에서는 어플리케이션과 정책이 복잡해지면 권한을 올바르게 부여하는 것이 어려울 수 있다는 것을 보여줍니다. 그림에서 왼쪽에는 4개의 기능과 2개의 리소스를 설명하는 serverless yaml파일이 있고, 오른쪽에서는 정점은 함수 또는 리소스이고, 엣지는 두 정점 사이에 허용되는 특정 작업을 나타내는 도달 가능성 그래프로 정책을 모델링합니다. 위 설명을 보면 Grasp는 완벽하지는 않지만, 이런 방법이 있다라는 것을 소개하는 것 같습니다.

## Grasp 설계
### 위협 모델 및 가정
이 연구에서는 클라우드 제공업체 외부의 공격자를 고려합니다. 이 공격자의 공격은 널리 알려진 공격을 기반으로 합니다. 이 연구에서는 클라우드 플랫폼에 액세스 권한이 없는 사용자는 비공개 기능 및 리소스와 상호 작용할 수 있는 취약점이 없다고 가정합니다. 그리고 플랫폼에서 시행되는 정책은 공격자가 수정하거나 변경할 수 없고, 정책의 잘못된 구성은 개발자의 오류 결과라고 가정합니다. 따라서 공격자의 공격은 보안 정책에 의해 공개로 선언된 기능 및 리소스를 통해서만 공격이 가능하다고 가정합니다.
### 설계 과제
* 다양한 상호 작용 :Serverless Application에서 함수는 다른 함수를 직접 호출하거나 이벤트 트리거를 통해 다른 함수를 간접적으로 호출할 수 있습니다. 그리고, 함수는 클라우드 인프라와 상호 작용하여 함수가 중개 라소스를 사용하여 서로간에 상태를 전파할 수 있습니다.
* IAM 정책의 다양성 : 함수 IAM 정책은 어플리케이션 모든 함수에 대해 전역적으로 정의하거나, 함수에 대해 개별적으로 정의하거나, 이 두 가지를 혼합할 수 있습니다. 그리고 리소스에 대한 정책은 어떤 컴포넌트가 해당 리소스에 액세스할 수 있는지를 지정할 수도 있습니다.
* 클라우드 서비스 API의 다양성 : Serverless Application은 독점적인 클라우드 API 서비스를 사용합니다. 이 서비스에는 해당 서비스 내에서 다양한 API를 호출할 수 있는 액세스 권한을 제공하는 고유한 API 및 권한 집합이 있습니다. 
### Grasp의 구조
* Knowledge Extractor : Serverless Application의 매니페스트 파일과 IAM 정책을 입력으로 받습니다. 이 과정에서는 매니페스트에서 함수, 리소스, 이벤트 트리거와 같은 기능적 요소를 추출하고, IAM 정책에서는 각 요소에 대한 권한 설정을 추출합니다.
* Serverless Access Control Model : 추출된 정보를 바탕으로 Grasp는 서버리스 애플리케이션에 특화된 추상화 모델을 구축합니다. 이 모델은 프롤로그 규칙으로 표현되며, 함수 간의 제어 흐름, 데이터 흐름, 이벤트 흐름을 정확히 모델링합니다. 예를 들어, 한 함수가 다른 함수를 호출하거나, 이벤트가 발생하여 함수가 자동으로 트리거되는 상황을 포함합니다.
* Policy Reasoner : 구축된 Serverless 액세스 제어 모델을 기반으로 Grasp는 IAM 정책을 추론하고 분석합니다. 각 함수나 리소스에 적용된 IAM 정책이 어떤 흐름을 허용하거나 제한하는지를 분석하여 보안적 문제나 권한 부여 오류를 식별합니다.
* Security Query Interface : 사용자는 보안 관련 쿼리를 Grasp에게 전달할 수 있습니다. Grasp는 이러한 쿼리에 대한 답변을 도달 가능성 그래프의 형태로 제공합니다. 이 그래프는 서버리스 애플리케이션의 구성 요소들 간의 관계와 IAM 정책에 의해 활성화된 흐름을 시각적으로 나타내며, 공격 경로나 잠재적으로 취약한 구성을 식별할 수 있습니다.
### Knowledge Extractor
Knowledge Extractor는 어플케이션의 시맨틱과 IAM 정책의 권한 시맨틱을 생성합니다.
* Modeling Application Semantics
    * Functions :name과 public_invoke(참이면 모든 권한이 없는 모든 유저도 인터넷을 통해 함수 호출이 가능하지만 거짓이면 권한이 있는 사용자만 사용 가능)를 수집합니다.
    * Resources : type, nane, public_read(참이면 리소스를 공개적으로 읽기 가능), public_write(참이면 리소스를 공개적으로 쓰기 가능)이 네가지 정보를 수집합니다. 
    * Events : 이벤트를 생성하는 리소스와 이벤트에 대한 응답으로 트리거되는 함수를 수집합니다.
* Modeling Access Control Semantics
    * Permission : 권한이 부여되는 함수, 부여되는 권한, 상태에 대응되는 리소스를 수집합니다.
    * Resource Access : 함수에 리소스에 대한 액세스 권한ㅇ을 정의하려면 해당 권한에 대한 지식뿐만 아니라 특정 리소스 유형에 대한 권한 지식도 필요합니다. 이러한 지식들은 클라우드 제공업체 설명서에서 확인할 수 있습니다.
### Serverless Access Control Model
Serverless Access Control Model은 어플리케이션 및 접근 제어 의미를 흐름의 의미로 확장하여 개발자가 기능 전반의 추론을 가능하게 합니다.
* Control Flows
함수 또는 일반 사용자가 다른 함수를 호출하여 데이터를 전달할 수 있을 때 발생합니다. 공개적으로 시작된 control flow는 Knowledge Extractor에서 나온 함수에 의해 묘사되고 내부 함수에 대한 control flow는 두 함수값을 사용하여 주어진 초기 함수 이름과 대상 함수를 호출할 수 있는 권한을 가진 함수를 찾습니다. 
* Data Flows
함수 또는 일반 사용자가 다른 함수가 읽을 수 있는 서비스에 쓸 수 있을 때 발생합니다. Data Flow는 초기 함소, 대상 함수, 데이터를 전달하는 데 사용되는 리소스 이름, 리소스에 쓰는 데 사용되는 권한, 리소스에서 릭는 데 사용되는 권한 이 다섯가지를 이용해 리소스에 쓸 수 있는 초기 함수와 리소스에서 읽을 수 있는 대상 함수를 찾습니다.
* Event Flows
함수 또는 일반 사용자가 함수 실행을 트리거하는 이벤트를 생성할 수 있을 때 발생합니다. Event Flow는 초기 함수, 대상 함수, 공유 리소스, 해당 리소스에 대한 액션, 액션이 주어진 리소스에 의해 생성된 이벤트 이 다섯 가지를 사진 규칙으로 표현됩니다.
### Security Queries
Grasp를 통해서 개발자는 쿼리를 정의해 어플리케이션의 IAM 정책의 보안 영향을 이해할 수 있습니다. Security Query는 공개적으로나 다른 함수를 통해 직접 혹은 간접적으로 액세스 할 수 있는 리로스의 도달 가능성 그래프를 정의합니다. 이 쿼리는 민감한 리소스에 대한 액세스 경로를 보호하기 위해 강화해야 하는 기능을 강조하고 어플리케이션의 IAM 정책을 수정하면 액세스 할 수 있는 리소스가 어떻게 변경되는지 설명합니다. 여기서는 공개적으로 노출된 구성 요소 탐지 쿼리, 읽기, 쓰기 및 경로 계산 쿼리, 비공개 데이터를 공용 리소스 쿼리로 유출하는 경로 계산에 중점을 둡니다.

## 구현
Grasp는 Serverless Framework로 만들어진 AWS Lambda Application의 보안 정책을 분석하기 위한 것입니다. 먼저 사용자는 Knowledge Extractor에 Serverless YAML파일을 넣게 되면, 그에 맞는 도달 가능성 그래프를 리턴해주게 됩니더. 이 그래프는 어플리케이션 구성 요소 간의 상호 작용을 설명하며, 공개적으로 접근 가능한 자원이나 공격자가 민감한 자원에 도달할 수 있는 경로를 식별할 수 있게 합니다. 그 다음에 유저는 그 그래프를 분석해서, 발생 가능한 취약점을 분석하게 되는 방식으로 구현됐습니다.

## Serverless 보안 정책 특성화
Grasp를 활용해 위에서 얻은 데이터 셋을 사용해 AWS Lambda 어플리케이션에 정의된 보안 정책에 대한 분석을 제공합니다.
### Application Complexity
어플리케이션의 복잡성은 함수 및 데이터 리소스의 수로 설명됩니다. 어플리케이션당 누적 함수 밀도는 아래 그림 제일 왼쪽에 있습니다. 그래프를 보면 대부분의 어플리케이션은 5개 이하의 함수를 갖고 있는 모습을 볼 수 있습니다. 다음으로 어플리케이션당 데이터 리소스 수 입니다. 아래 그림에서 가운데 있는 그래프이고 대부분 5개 이하의 리소스를 가지고 있는 모습을 볼 수 있습니다. 
### Policy Complexity
아래 그림에서 제일 오른쪽에 있는 그래프는 어플리케이션당 정책 문장 수를 나타냅니다. 그래프를 보면 대부분의 정책이 대부분 10개 이하의 문장으로 구성된 모습을 볼 수 있습니다.
### Function-Resource Connectivity
어플리케이션의 연결성 비율은 허가된 함수-리소스 흐름의 수를 가능한 함수 * 리소스로 나눈 값으로 정의 됩니다. 맨 아래의 사진을 보면 30% 이상의 어플리케이션이 연결성 비율이 1입니다. 이는 높은 허가 정책을 갖고 있다는 것을 의미합니다. 이는 매우 포괄적인 보안 정책이라는 것입니다.

### Wildcards
Grasp는 Wildcard를 주체와 객체에 적용되는 구체적인 명령문으로 확장하여 Wildcard의 효과를 정확하게 정량화할 수 있습니다.
* 전체 와일드카드
권한 필드에 전체 와일드카드가 사용된 정책 문장은 모든 어플리케이션에서 6개, 리로스 필드에 전체 와이들카드가 사용된 문장 347개, 전체 와일드카드 리소스에 대해 전체 와일드카드 권한이 부여된 경우는 2건을 찾았습니다.
* 부분 와일드카드
권한 필드에 부분 와일드카드가 사용된 설명은 160개, 리소스 필드에 사용된 부분 와일드 카드가 사용된 문장 41개, 부분 와일드카드 리소스에 대해 부분 와일드 카드 권한이 포함된 정책은 1권을 찾았습니다.    
이를 조합해 와일드카드 리소스에 대한 와일드카드 권한이 지정된 정책 문장은 총 130건이었습니다. 이를 통해서 와일드카드 사용이 과도한 허용적인 정책을 만들어내는 모습을 확인하고 경고를 제공할 수 있습니다.
### Grasp Queries
* Publicly Exposed Components
완전히 공개된 어플리케이션은 공격자가 직접 액세스 할 수 있기에 매우 민감합니다. 그렇기에 허용 정책이 비공개 리소스애 대한 간접 액세스를 허용할 수 있으므로 보안 정책의 정확성을 검증하는 것이 중요합니다. 또한 공개 리소스도 민감합니다. 하지만 리소스는 공개 리소스라고 해서 항상 잘못 구성된 정책은 아닙니다. 따라서 공개 리소스에 대한 주의깊은 감사가 필요합니다. Grasp는 분산된 보안 정책을 단일 그래프를 통합함으로써 이 작업을 간소화시켜줍니다.
* Read, Write, Read/Write Path
공격자가 제어하는 입력으로 인해 리소스에 액세스 할 수 있는 경로가 존재하면 비공개 리소스도 취약할 수 있습니다. 이를 Grasp는 이 경로를 확인하였습니다. 이 경로가 있다고 해서 반드시 IAM 정책이 잘못된 것은 아니지만 개발자는 이 발견된 경로를 유심히 살펴야합니다.
* Exfiltrate to Public Resource
만약 공격자가 비공개 리소스에 대한 읽기 액세스 권한을 얻은 경우 정책적으로 허용된 데이터 유출 방법을 식별해야합니다. Grasp는 공개 사용자가 공개 함수를 호출해 비공개 리소스에서 읽은 다음 공개 리소스에 쓸 수 있는 경로를 발견했습니다. 이게 무조건 취약하다는 것은 아니지만 충분히 위험성이 있으므로 개발자는 주의깊게 감시하는 것이 필요합니다.
* Performance
Grasp는 731개의 어플리케이션 정책을 분석하면서 1개를 제외한 모든 정책이 1초 이내에 완료됐습니다. 가장 긴 시간도 3.9초 였고, 이를 보면 IAM 정책에 대한 결과를 매우 빠르게 반환한다는 것을 볼 수 있습니다.
### Policy Hardening Case Study
#### Shan18/Flash 
Shan18/Flash 어플리케이션은 사용자가 자체 신경만 모델을 생성, 훈련 및 배포할 수 있는 엔드 투 엔드 딥러닝 플랫폼을 생성합니다. Grasp가 이 어플리케이션에 대한 경로를 생성했을 때 아래 그림과 같이 전과는 달리 축소된 모습을 볼 수 있었습니다. 이전에는 전역 권한을 가져 다 읽고, 쓰고 접근할 수 있었지만, 불필요한 접근을 줄여서 오른쪽과 같이 만들 수 있었습니다. 실제로 이를 Github 이슈를 개설해서 연락을 취해 소유자에게 알렸습니다.

## 결론
이 논문에서는 Serverless Application을 위한 자동 정책 분석 프레임워크 Grasp를 소개했습니다. Grasp는 어플리케이션 내에서 데이터 흐름과 실행을 포착하는 Serverless 보안 정책을 위한 로직 기반 모델입니다. 이 모델을 통해 도달 가능성 그래프를 얻고, 그 그래프를 통해서 사전에 유출 경로를 확인 후 조치를 취할 수 있습니다. 실제로 Grasp를 이용해 조사했을 때 92%가 정책이 10개의 문장으로 구성되어있고 그 중 30%는 모든 어플리케이션 기능과 리소스에 대해 완전한 도달 가능성을 갖고 있는 것도 확인했습니다. 이를 Grasp를 통해 방지할 수 있습니다.
